# ГЛАВА 2. ПРАКТИЧЕСКАЯ ЧАСТЬ

Практическая часть исследует, какие тестовые случаи можно удалить из набора SchemaAnalyst, не теряя исходные требования покрытия и наблюдаемые граничные случаи простых целочисленных CHECK. Для этого исходная Java-система генерирует набор и запускает штатные редукторы, C++-прототип дополнительно выбирает тесты с учётом границ, а PostgreSQL проверяет фактический результат SQL. Алгоритмы генерации и штатные редукторы SchemaAnalyst не изменялись.

В главе отдельно описываются реализованные компоненты, подтверждённые запуском результаты и ограничения эксперимента. Детальная сводка, включая хеши исходных наборов и результаты PostgreSQL, приведена в [RESULTS_BASELINE.md](./RESULTS_BASELINE.md).

## 2.1 Постановка задачи и ограничения реализации

В эксперименте для каждой пары «генератор, seed» один раз создаётся исходный `TestSuite`. В `TestCase` поле `state` содержит подготовительные строки, необходимые для состояния базы, а `data` — строки проверяемого теста; тест также связан с исходным требованием и ожидаемым результатом. Для анализа передаются описание CHECK, сведения о строках и идентификаторы требований, которые тест покрывает.

Исходный Java-объект сохраняется в файл `.ser`, а экспортёр формирует используемый C++ и валидатором JSON `*-full.json`. Ниже — сокращённый иллюстративный пример одной записи из массива `tests`; полный JSON также содержит генератор, схему, список требований и SHA-256 исходного `.ser`:

```json
{
  "id": "T2",
  "sourceRequirementId": "R1",
  "coveredRequirementIds": ["R1"],
  "expectedResult": true,
  "state": [
    {"table": "parent", "values": {"id": "1"}}
  ],
  "data": [
    {
      "table": "sample",
      "values": {
        "id": "2",
        "parent_id": "1",
        "code": "2",
        "amount": "10",
        "ceiling": "50",
        "floor": "1"
      }
    }
  ],
  "stateSql": ["INSERT INTO parent (id) VALUES (1);"],
  "dataSql": [
    "INSERT INTO sample (id, parent_id, code, amount, ceiling, floor) VALUES (2, 1, 2, 10, 50, 1);"
  ],
  "stateInsertCount": 1,
  "dataInsertCount": 1
}
```

В этом примере сначала в `state` создаётся родительская строка для внешнего ключа, затем в `data` проверяется строка `sample`. Значения удовлетворяют ограничениям схемы, поэтому `expectedResult` равен `true`. Пример иллюстрирует структуру записи, а не утверждает, что именно этот `TestCase` попал в базовый запуск.

Цель boundary-aware редуктора — выбрать подмножество исходных целых `TestCase`, которое сохраняет:
1. все требования SchemaAnalyst, покрытые исходным набором;
2. все граничные наблюдения поддерживаемых целочисленных сравнений, которые присутствуют в исходном наборе и подтверждены PostgreSQL.

Редуктор не генерирует новые тесты: отсутствующее в исходном наборе значение не считается сохранённым или недостижимым. Оно просто не входит в множество доступных для сохранения граничных наблюдений. Генерация дополнительных кандидатов не входит в реализацию.

Реализованный MVP анализирует простые реляционные CHECK с операторами `<`, `<=`, `>` и `>=` в двух формах:

- сравнение целочисленного столбца с константой: `x op c`;
- сравнение двух целочисленных столбцов: `x op y`.

Для значений столбцов реализованы типы PostgreSQL `INTEGER` и `BIGINT`; числовые константы должны разбираться как целые. Соседние значения определяются с шагом в единицу. C++ вычисляет разность в `__int128`, чтобы разность значений `BIGINT` не переполнялась. Десятичные константы, хотя экспортёр представляет числовые константы общим типом `NumericValue`, в C++ не поддерживаются.

В MVP не входят произвольные арифметические выражения, `NUMERIC`, вещественные типы, функции PostgreSQL, массивы, JSON-выражения и общий анализ составных CHECK. NULL учитывается отдельными категориями и не считается числовым смещением.

Собственный C++-алгоритм выбирает целые `TestCase` из исходного JSON и не объединяет состояния. Штатный STICCER рассматривается отдельно: он может объединять тесты, поэтому его результат не обязательно является подмножеством исходных тестовых случаев.

## 2.2 Архитектура решения

Практическая система состоит из SchemaAnalyst, Java-снимка/экспортёра, C++-компонента `test_suite_minimization` и отдельного PostgreSQL oracle. Все четыре компонента были задействованы в эксперименте с четырьмя генераторами и независимыми запусками штатных редукторов.

### 2.2.1 SchemaAnalyst

SchemaAnalyst хранит схему в Java-модели `Schema`. Критерий покрытия создаёт объект `TestRequirements`, после чего `TestSuiteGenerator.generate()` строит `TestSuite`. Каждый `TestCase` содержит исходное требование, начальное состояние `state` и проверяемые данные `data`.

Класс `ReductionFactory` выбирает штатный метод сокращения. В исследованной версии доступны `simpleGreedy`, `additionalGreedy`, `HGS`, `random` и `sticcer`. Общий класс `Reduction` строит соответствие между тестами и требованиями в `contextTableCreator()`, собирает выбранные тесты в `getReducedTestSuite()` и проверяет покрытие в `checkCoverage()`.

SchemaAnalyst остаётся источником исходных тестов и базовой реализацией для сравнения. Изменять его алгоритмы генерации ради эксперимента не требуется.

### 2.2.2 Преобразование в JSON

Java-классы `GenerateBaselineSnapshot`, `ExportBaselineJson` и `RunSnapshotReducer` сохраняют сериализованный исходный набор и экспортируют структуру схемы, тестов, требований и вставок в JSON формата 1. Каждый редуктор заново читает один и тот же `.ser`-снимок; результат предыдущего редуктора не используется. SHA-256 исходного снимка включён в результаты для контроля идентичности входа. Формат описан в [FORMAT.md](../test_suite_minimization/experiments/FORMAT.md).

### 2.2.3 Компонент `test_suite_minimization` на C++

Компонент читает JSON и выполняет детерминированный жадный отбор. Покрытие SchemaAnalyst он получает из `coveredRequirementIds`, которые заранее рассчитывает Java-экспортёр; C++ не исполняет заново произвольные предикаты SchemaAnalyst. Граничные наблюдения C++ вычисляет по данным теста, но засчитывает только при подтверждённом результате PostgreSQL: успешной вставке либо отказе целевого CHECK с SQLSTATE `23514` и совпадающим именем ограничения. Отчёт включает выбранные тесты, покрытия до и после выбора, потери, неподдерживаемые CHECK и кандидаты границ без подтверждения.

### 2.2.4 Тестовая база PostgreSQL

PostgreSQL используется как внешний oracle фактического выполнения. Валидатор применяет фиксированное описание таблиц из `experiments/schema.sql`; перед каждым тестом он удаляет и заново создаёт схему `public`. Затем выполняет SQL из `state` и `data` в указанном порядке. Локальный PostgreSQL 18.7 на `127.0.0.1:55432` использовался в базовом эксперименте. Для теста сохраняется один результат с фазой выполнения, SQLSTATE первой ошибки, именем ограничения и сообщением. Если подготовительные вставки `state` завершаются ошибкой, это не считается ожидаемым отказом проверяемых данных.

Таблица 2.1 показывает фактический статус компонентов.

| Компонент | Назначение | Состояние |
|---|---|---|
| SchemaAnalyst | Построение требований, генерация и штатное сокращение | Исходный код изучен, проект собран |

## 2.3 Формат входных и выходных данных

JSON-формат ниже соответствует реализованному обмену версии 1; описание полей и PostgreSQL evidence находится в [FORMAT.md](../test_suite_minimization/experiments/FORMAT.md).

В корневом документе хранятся следующие поля:

- `formatVersion` — версия формата;
- `schema` — таблицы, столбцы, типы и поддерживаемые CHECK;
- `generation` — критерий, генератор, seed, бюджет, время генерации и счётчики требований;
- `requirements` — исходные требования покрытия;
- `tests` — полный список тестов;
- `schema.tables` и `schema.checks` — структура таблиц и поддерживаемые CHECK.

Исходные тесты имеют идентификаторы вида `T1`, `T2`, ...; новый тест, сформированный при объединении STICCER, получает идентификатор вида `M1`. Тест содержит `sourceRequirementId`, список `coveredRequirementIds`, `state`, `data`, SQL-вставки и число вставок. Экспортёр повторно рассчитывает покрытие требований для тестов, которые он экспортирует, через `PredicateChecker`; для boundary-aware набора исходные идентификаторы покрытия переносятся вместе с выбранными тестами. Строка содержит имя таблицы и значения столбцов. NULL передаётся JSON-значением `null`, целые значения — десятичными строками, чтобы точно сохранить `BIGINT`.

Для CHECK передаются идентификатор ограничения, таблица, исходное выражение, признак поддерживаемости, оператор и операнды. Операнд задан как ссылка на столбец либо числовая константа. Экспортёр помечает как поддерживаемые простые реляционные выражения с одним или двумя операндами-столбцами и операторами из MVP; C++ дополнительно распознаёт только `IntDataType`, `BigIntDataType` и целые значения. Тип столбца, не входящий в этот перечень, не даёт числовых граничных наблюдений; из-за разделения проверки между экспортёром и C++ он не обязательно попадёт в список `unsupportedChecks`. Для SQL oracle отдельно сохраняются `stateSql` и `dataSql`.

Сокращённый пример фактической структуры:

```json
{
  "formatVersion": 1,
  "generation": {
    "criterion": "CondAICC",
    "generator": "avsDefaults",
    "seed": 0,
    "budget": 10000
  },
  "schema": {
    "checks": [
      {
        "id": "amount_min",
        "table": "sample",
        "expression": "amount >= 10",
        "supported": true,
        "operator": ">=",
        "left": {"kind": "column", "table": "sample", "column": "amount", "type": "IntDataType"},
        "right": {"kind": "constant", "value": "10", "type": "NumericValue"}
      }
    ]
  },
  "requirements": [
    {"id": "R1", "expectedResult": true, "failedDuringGeneration": false}
  ],
  "tests": [
    {
      "id": "T1",
      "sourceRequirementId": "R1",
      "coveredRequirementIds": ["R1"],
      "expectedResult": true,
      "state": [],
      "data": [
        {"table": "sample", "values": {"amount": "10"}}
      ],
      "stateSql": [],
      "dataSql": ["INSERT INTO sample (amount) VALUES (10);"],
      "stateInsertCount": 0,
      "dataInsertCount": 1
    }
  ]
}
```

Выход C++-компонента содержит:

- список `selectedTestIds`;
- число исходных и выбранных тестов и вставок `state`/`data`;
- множества требований и границ до и после сокращения;
- `lostObligations`, `unsupportedChecks` и `unverifiedBoundaryTestIds`;
- причину выбора каждого теста;
- время отбора;
- SHA-256 исходного `.ser`-снимка.

Контрольная сумма подтверждает, что разные методы запускались от одного и того же исходного снимка. Для штатных редукторов Java-экспортёр вычисляет `coveredRequirementIds` заново для каждого результирующего `TestCase` через `PredicateChecker`. Boundary-aware вариант выбирает тесты из исходного JSON и переносит уже рассчитанные для этих тестов идентификаторы; C++ проверяет объединение этих идентификаторов, но не запускает `PredicateChecker`. Поэтому проверка покрытия требований в C++ является проверкой сохранения переданных идентификаторов, а не независимым повторным вычислением предикатов по SQL.

## 2.4 Правила выделения граничных проверок

В текущей реализации граничное наблюдение задаётся идентификатором CHECK, категорией разности и результатом сравнения. Отдельного идентификатора атома внутри CHECK нет: анализатор поддерживает только одно простое реляционное выражение на CHECK. В отчёте наблюдение записывается как `B|<check-id>|<distance>|<truth>`, например `B|amount_min|0|true`; для NULL вместо числового смещения указывается категория `left-null`, `right-null` или `both-null`, а результат — `unknown`.

Для сравнения `x op c` вычисляется разность

`d = x - c`.

Для сравнения `x op y` вычисляется

`d = x - y`.

Числовыми граничными категориями являются только `d = -1`, `d = 0` и `d = 1`. Остальные значения могут участвовать в обычном покрытии SchemaAnalyst, но не считаются непосредственной окрестностью границы. Смысл результата определяется исходным оператором. Например, при `x >= c` категории `-1`, `0`, `1` дают соответственно FALSE, TRUE и TRUE. При `x < c` эти категории дают TRUE, FALSE и FALSE.

Если один из операндов равен NULL, числовая разность не вычисляется. Такие случаи фиксируются отдельно как `left-null`, `right-null` или `both-null`. Они нужны для проверки трёхзначной логики SQL, но не входят в число покрытых позиций −1, 0 и +1.

Разность для `INTEGER` и `BIGINT` нельзя вычислять в типе той же разрядности без дополнительной проверки. Например, вычитание из максимального `BIGINT` минимального может переполниться. Реализация C++ использует знаковое `__int128`; значения в JSON передаются строками, чтобы не потерять точность при экспорте.

Одного совпадения чисел недостаточно для зачёта границы. C++ рассматривает только строки `data` целевой таблицы, в которых присутствуют значения обоих операндов. Для теста с ожидаемым отказом PostgreSQL должен указать именно целевой CHECK; ошибка внешнего ключа, первичного ключа, `NOT NULL` или другого ограничения не подтверждает этот CHECK. Успешная вставка учитывается как подтверждение только тогда, когда фактический результат совпал с ожидаемым результатом теста.

Для простых одиночных CHECK в подготовленной схеме предполагается следующая идентификация:

- `amount >= 10` — форма `x op c`;
- `amount <= ceiling` — форма `x op y`;
- `ceiling < 100` — форма `x op c`;
- `floor > 0` — форма `x op c`.

Составные выражения с `AND` и `OR` требуют дополнительно установить, не маскирует ли другой атом результат целевого сравнения. Общий анализ таких выражений не реализован и не входит в заявленный MVP. Ручной NULL-oracle используется только как проверка семантики конкретного выражения `x > 0 AND y > 0`.

## 2.5 Алгоритм отбора и проверка покрытия

Пусть `T` — исходный набор тестов. По данным полного набора и результатам PostgreSQL строятся два множества:

- `R` — исходные требования SchemaAnalyst, для которых Java-экспортёр нашёл покрывающий тест в полном наборе;
- `B` — граничные наблюдения, найденные в `data` полного набора и подтверждённые результатом PostgreSQL.

Полное сохраняемое множество имеет вид `U = R ∪ B`. Для каждого теста `t` строится множество `C(t)` из переданных идентификаторов требований и подтверждённых границ. В одном запуске C++ матрица `C(t)` после построения не изменяется. Штатные Java-редукторы получают отдельные повторно загруженные копии снимка, поэтому изменение descriptors при их работе не меняет входные данные других редукторов.

Boundary-aware редуктор выполняет следующие шаги:

1. Проверяет формат входа и уникальность идентификаторов тестов; при анализе границ учитывает поддерживаемые экспортёром CHECK и распознаваемые целочисленные значения.
2. Строит `R`, `B` и матрицу `C(t)` для полного набора.
3. Добавляет тесты, которые являются единственными свидетелями хотя бы одного элемента `U`.
4. Пока остаются непокрытые элементы, выбирает тест с наибольшим числом новых элементов.
5. При равенстве выбирает тест с меньшим числом SQL-вставок, затем с меньшим исходным идентификатором.
6. Проходит по выбранным тестам в обратном порядке и удаляет тест, если после удаления покрытие `U` не меняется.
7. Формирует список выбранных тестов и объяснение для каждого выбора.

Правило равенства делает результат воспроизводимым. Учёт числа вставок используется только после сравнения полезности по покрытию, поэтому более короткий тест не может заменить единственного свидетеля требования.

Внутри отбора C++ проверяет, что выбранные тесты покрывают всё `U` из входной матрицы. Сценарий матрицы затем отдельно валидирует выбранный набор в PostgreSQL, запускает C++ на выбранных тестах и сравнивает полученные множества с исходными `R` и `B`. Идентификаторы `coveredRequirementIds` предварительно вычисляет Java-экспортёр через `PredicateChecker`; C++ использует их для штатных требований, а границы повторно вычисляет по данным строк и PostgreSQL evidence. Для успешного результата должны выполняться условия

`R(selected) = R(full)`

и

`B(selected) = B(full)`.

Если равенство нарушено, сокращение отмечается как потеря покрытия, а в отчёт записывается разность множеств. Если `B(full)` пусто, текущая матрица показывает нулевое число границ; равенство пустых множеств выполняется формально и не подтверждает сохранение непустого набора граничных случаев.

Дополнительная PostgreSQL-проверка запускает каждый выбранный тест в чистом состоянии. Она подтверждает, что фактическое принятие или отклонение SQL соответствует ожидаемому результату. Эта проверка дополняет расчёт покрытия, но не заменяет его: одинаковый результат вставки может возникнуть по разным причинам.

Реализация находится в `test_suite_minimization/cpp/`; обработка PostgreSQL evidence и независимые запуски описаны в `test_suite_minimization/experiments/`.

## 2.6 Реализация и существующие файлы

В репозитории сохранена исходная реализация SchemaAnalyst и добавлены компоненты экспериментального обмена и сокращения. Основные части приведены в таблице 2.2.

## 2.7 Методика сравнения со штатными методами

Сравнение отделяет генерацию тестов от их сокращения. Для каждой комбинации генератора и seed набор создаётся один раз и сохраняется в `.ser`; его SHA-256 включается во все результаты сокращения.

Для каждого штатного метода `RunSnapshotReducer` заново десериализует исходный `.ser`. Результат предыдущего редуктора не используется как вход следующего. Это особенно важно для STICCER, который может объединять тесты, и для кода SchemaAnalyst, который добавляет descriptors к объектам требований при построении таблицы покрытия. C++ boundary-aware reducer работает с экспортом того же снимка.

В минимальную матрицу сравнения входят:

- критерий `CondAICC`;
- генераторы `avsDefaults`, `randomDefaults`, `dominoRandom` и `dominoAVS`;
- методы `none`, `simpleGreedy`, `additionalGreedy`, `HGS`, `random` и `sticcer`;
- начальный seed 0;
- бюджет генерации 10000 вычислений;
- `readability=false` и `fullreduce=false`.

`none` сохраняет исходный набор и используется как контроль. Параметр `fullreduce=false` нужен, чтобы сокращение строк внутри теста не смешивалось с последующим отбором тестовых случаев.

Полученная матрица является пилотным запуском одного seed (0), а не статистической выборкой. Для обобщающих выводов нужен заранее зафиксированный список seeds, например 30 seeds, и отдельный повтор всех комбинаций. Результаты smoke и настройки запуска в основную выборку не включаются.

`summary.csv` матрицы содержит для каждой пары «генератор, seed, редуктор» статус, SHA-256 исходного снимка, время генерации, число исходных и итоговых тестов, число `state` и `data` INSERT до и после сокращения, время сокращения, числа покрытых требований и граничных наблюдений до и после, потерянные идентификаторы, неподтверждённые кандидаты и сводку результатов PostgreSQL. Связанные JSON содержат состав тестов и вставок; `*-postgres.csv` — по одной строке результата на тест; логи и `environment.log` фиксируют вывод процессов и версии используемых инструментов. Исходные требования, неудачные при генерации, отражаются в JSON снимка, а не отдельной колонкой `summary.csv`. Мутационный анализ в этой матрице не запускался.

Время генерации измеряется вокруг `TestSuiteGenerator.generate()`. Время штатного сокращения — вокруг вызова Java-редуктора; для `boundaryAware` берётся `selectionNanoseconds` C++-отбора. Эти измерения не включают запуск JVM и PostgreSQL-валидацию; отдельные времена загрузки JSON и построения C++-матрицы не записываются как самостоятельные метрики. Для оценки стохастических методов нескольких запусков недостаточно: медиану и разброс следует рассчитывать по заранее зафиксированному набору seeds, а не по одному seed.

### 2.7.1 Схемы для проверки

Подготовленная `CourseworkSchema` содержит таблицу `parent` и таблицу `sample`. В ней есть первичный ключ, внешний ключ, UNIQUE, NOT NULL и четыре CHECK:

- `amount >= 10`;
- `amount <= ceiling`;
- `ceiling < 100`;
- `floor > 0`.

Эта схема проверяет обе поддерживаемые формы сравнения и взаимодействие с другими ограничениями. Она не покрывает составные ключи и сложные логические выражения. Поэтому после отладки нужны отдельные небольшие схемы для составных PK, UNIQUE и FK, nullable `AND`/`OR`, маскирующих CHECK и предельных значений `INTEGER` и `BIGINT`.

### 2.7.2 Проверка в PostgreSQL

Перед каждым тестом валидатор удаляет схему `public`, создаёт её заново и подключает фиксированный файл `schema.sql`. Затем он запускает SQL-вставки `state` и по их успешному завершению — вставки `data`. Следующие тесты выполняются независимо, даже если предыдущий завершился ожидаемым отказом.

Список SQL-команд и их порядок сохраняются в JSON. В PostgreSQL CSV записывается одна строка на тест: ожидаемый и фактический результат, фаза (`reset`, `state`, `data` или `missing`), первая ошибка, её SQLSTATE, имя ограничения и сообщение. При ошибке в `state` тест помечается как ошибка подготовки и не засчитывается как ожидаемый отрицательный тест. При ошибке в `data` валидатор останавливается на первой неуспешной вставке; CSV не является журналом каждой успешно выполненной SQL-команды.

### 2.7.3 Обработка сбоев

При штатном завершении матрица записывает ошибки фаз в `failures.csv`, а вывод команд — в отдельные логи; версии инструментов и параметры среды — в `environment.log`. В сводке различаются `NOT_RUN`, ошибки генерации/экспорта/редукции, ошибки PostgreSQL и потери покрытия. В реализации нет тайм-аутов процессов и статуса `TIMEOUT`; кроме того, ранний `throw` на этапах настройки или сборки может завершить сценарий до записи итогового `summary.csv` и `failures.csv`. Поэтому при сбое нужно сверять сохранённые логи, а не считать отсутствие строки нулевым результатом.

Бюджет `10000` — бюджет попыток генерации данных, а не ограничение времени. Недостигнутое при генерации требование отражается в отчёте генерации как не покрытое; это не доказывает его невозможность и не должно трактоваться как доказательство отсутствия подходящего теста.

## 2.8 Фактические результаты, ограничения и выводы

Полная таблица измерений и raw CSV приведены в [RESULTS_BASELINE.md](./RESULTS_BASELINE.md). В пилоте использованы четыре генератора, seed 0, бюджет 10000 и независимые копии каждого исходного снимка для шести штатных методов. Дополнительно выполнен C++ `boundaryAware`.

Генерация дала 24 теста для `avsDefaults`, `randomDefaults` и `dominoRandom`, и 16 тестов для `dominoAVS`. Время генерации составило соответственно 144.665, 837.871, 72.647 и 447.058 ms. PostgreSQL подтвердил ожидаемый результат для всех строк четырёх исходных наборов и всех 28 результатов редукции.

Boundary-aware вариант сохранил все обнаруженные подтверждённые требования и границы, выбрав 18, 16, 17 и 11 тестов соответственно. На исходном `avsDefaults` штатные `simpleGreedy`, `additionalGreedy`, `HGS` и `random` потеряли разные числовые границы. STICCER минимизировал набор сильнее, но потерял штатные требования во всех четырёх запусках и одну исходную границу в `dominoRandom`. Для ряда тестов SQL завершился ошибками PK, FK, NOT NULL или другого CHECK; эти строки не засчитывались как свидетельство целевой границы.

Число наблюдений после STICCER иногда превышает исходное: объединение тестов может создать новое сочетание значений, например категорию `both-null` или новую числовую позицию. Поэтому сравниваются идентификаторы множеств, а не только их размеры; наличие новых наблюдений не отменяет потерю других исходных обязательств.

### Ограничения и неподтверждённые предположения

- Измерен только один seed и одна схема. Результат показывает конкретные потери и сохранение на этих снимках, но не статистическое преимущество методов.
- Граница считается доступной, только если она встречается в исходном наборе и подтверждается PostgreSQL. Отсутствие значения `-1`, `0` или `+1` — не доказательство его невозможности.
- MVP не анализирует произвольные составные CHECK, арифметические выражения и mutation score.
- В полном Java test report сохранено 15 ошибок из 1715 тестов; основные сообщения связаны с несовместимостью PostgreSQL SCRAM с legacy JDBC, `NullPointerException` в старых case-study tests и несовпадением ожидаемого количества мутантов. Они отделены от успешной матрицы PostgreSQL; подробности и ссылки приведены в baseline report.

### Выводы по практической части

Цепочка Java snapshot → JSON → C++ reducer → PostgreSQL oracle реализована и проверена. Штатные редукторы сохраняют обычные требования, но на одном из исходных наборов некоторые из них потеряли наблюдаемые числовые границы. Boundary-aware прототип сохранил полный набор подтверждённых обязательств на всех четырёх запусках.

Рекомендуется продолжить разработку boundary-aware reducer, но не считать пилот доказательством общей эффективности. Для следующего этапа необходимо заранее зафиксировать набор seeds, расширить набор схем и повторить матрицу на независимых снимках, сохраняя различие между подтверждёнными и неподтверждёнными boundary-кандидатами.
